Popfly · Marketing Infrastructure

Identity Server → Reach, direct.

A first-party endpoint on the site's own origin that issues durable visitor identity, logs every attribution touch and every pageview, classifies each touch to a channel, and delivers validated form events straight to Reach. n8n leaves the form path. Reach owns all ETL.

SPEC v3.2STATUS Build-ready · two decisions reopenedHOST Webflow Cloud @ /eDATE Jul 31, 2026

Every claim in this spec carries its epistemic status:

Observed — confirmed in code, data, or docs Inferred — reasoned from evidence Assumed — verify before relying on it Decided ✓ New in v3.2

What changed from v3.1

  1. Pageviews are now in scope. New pageviews table. touches stays an attribution log; the two are separate on purpose.
  2. Touches are now classified to a channel at write time. v3.1 stored raw params and pushed the taxonomy onto the Reach ETL owner. It now ships with the data, versioned.
  3. A read path exists. v3.1 had no way to get touch history out of D1 except on form submit, which excluded every visitor who never converted. That was the largest architectural gap.
  4. RB2B moved from "out of scope" to a join dependency. RB2B will never supply UTM data (see §3), so this touch log is the only channel source for RB2B-identified people.
  5. Session derivation moved server-side; bot gate added to /e/v; owned-domain suppression; cookie scope decided.
  6. New §6 documents the metrics this unlocks and, more importantly, the four it does not.

§3Current state this builds on

  • Observed  Head script (deployed): visitor_id in localStorage, session ID in sessionStorage, first-touch object with sessionStorage migration shim, grsf cookie for GrowSurf, window.PopflyTracking.getFormValues() interface, hidden-field population on load + capture-phase submit, ?debug=pf flag. First-touch only.
  • Observed  Footer script: deleted — was overwriting UTM fields from stale sessionStorage keys.
  • Observed  Form: one Webflow form at popfly.com/start/new; hidden fields match getFormValues() names.
  • Observed  RB2B will never supply channel data. Their KB article Access to UTM Parameters and Other Identifiers (updated Dec 10, 2025) states RB2B intentionally limits UTM display in the dashboard, CSV exports, and most integrations, and surfaces it only through the HubSpot and Salesforce CRM integrations. The webhook payload is fixed and contains no UTM fields. api.rb2b.com is an identity-resolution product (IP→HEM, email→LinkedIn), not a feed of your own visitors. Consequence: this touch log is the sole channel source for RB2B-identified people.
  • Observed  Referrer values seen in production (RB2B daily export, 479 profiles): google.com, l.threads.com, bing.com, facebook.com, duckduckgo.com, linkedin.com, instagram.com, search.yahoo.com, chatgpt.com, substack.com, android-app://com.google.android.gm, android-app://com.linkedin.android, and — critically — guide.popfly.com and app.popfly.com. The classifier must handle the android-app:// scheme and must suppress owned domains.
  • Observed  Zero query strings survive in RB2B's export. All 675 page-URL entries are bare paths. This is RB2B's export behavior, not a Popfly tagging failure, and it is why the unknown/direct split has to be built here.
  • Assumed  Reach ingestion (April spec): POST with ?key= validated against WEBHOOK_SOURCE; email required; normalizer sets eventType. Confirm unchanged before dual-write.
  • Assumed  Volume: ~20k form events/mo ceiling. Pageview volume is unknown and materially larger. RB2B logged 675 pageviews across its identified slice at a stated 5–20% resolution rate, implying total pageviews of a different order. Business plan allows 2M Cloud requests/mo, which is ample; D1 write limits under Webflow Cloud's allocation are the binding constraint and are unverified. See §9.

POST /e/v — identify + touch + pageview, one roundtrip per pageload

Body from script: { url, referrer, session_hint, params, rb2b_id? }

  1. Bot gate New: UA check against a known-crawler list. Flag, never drop — sets is_bot on both rows. Same principle as /e/collect. AdsBot-Google-Mobile and preview fetchers otherwise mint cookies and pollute channel counts.
  2. Read pf_vid cookie; missing → mint v_<uuid>.
  3. Set-Cookie: pf_vid=…; Domain=.popfly.com; Path=/; Max-Age=34560000; HttpOnly; Secure; SameSite=Lax — reissued every call (rolling 400-day expiry, the Chrome cap). Domain is new in v3.2 so the ID is readable from app.popfly.com and guide.popfly.com when those surfaces are instrumented later.
  4. Session derivation, server-side New: session = last session for this visitor_id if its last event is under 30 minutes old, else mint a new one. The client's sessionStorage value is accepted as a hint only. v3.1 trusted the client, which meant two open tabs produced two sessions and double-counted touches.
  5. Always write a pageviews row.
  6. Touch decision: classify first (see below). Write a touches row iff channel is not internal and (new session, or attribution param present, or external referrer) and dedup_key is not already present. Plain internal navigation logs a pageview and nothing else — touches stays an attribution log.
  7. Return { visitor_id, session_id }. Same-origin → no CORS. Cache-Control: no-store.

Why the server cookie beats the localStorage ID: HttpOnly and set by the first-party origin, so it sits outside ITP's 7-day script-storage cap and survives localStorage clears. The localStorage ID stays as fallback and continuity for existing visitors.

Why pageviews are nearly free: the /e/v call already fires on every pageload in v3.1 and the server was discarding the navigation. Adding pageviews costs zero additional HTTP requests. The only new cost is D1 writes.

Channel classification New

Runs server-side in lib/classify.ts. Ordered, first match wins. Raw params and referrer are always stored unmodified alongside the derived values, so nothing is lossy.

 1. gclid | gad_source | gad_campaignid   → paid_search      / google
 2. msclkid                               → paid_search      / bing
 3. li_fat_id                             → paid_social      / linkedin
 4. grsf                                  → referral_program / growsurf
 5. utm_medium ∈ {cpc,ppc,paid,
                  paidsocial,display}     → paid_*           / utm_source
 6. utm_source or utm_medium present      → map from taxonomy
 7. referrer host ∈ SEARCH_ENGINES        → organic_search
 8. referrer host ∈ SOCIAL                → organic_social
 9. referrer host ∈ AI_SURFACES           → ai_referral
10. referrer host ∈ OWNED_DOMAINS         → internal  (suppress touch)
11. referrer present, no match            → referral
12. no referrer, no params                → direct
13. else                                  → unknown

Rule 1 must precede rule 6. With Google Ads auto-tagging on and manual UTMs off, a paid click arrives with gclid and no utm_source. If UTM checks run first, every paid click classifies as direct and the conclusion is that ads do not work.

Rules 12 and 13 stay separate. direct is a real behavior. unknown is a data gap. Collapsing them hides exactly the bare-landing-page-URL failure class already seen in paid campaigns.

Host lists

  • OWNED_DOMAINS: popfly.com, www.popfly.com, app.popfly.com, guide.popfly.com. All four appear as referrers in production data. Without suppression, a www → app → www bounce logs a spurious touch classified as referral.
  • AI_SURFACES: chatgpt.com, perplexity.ai, claude.ai, gemini.google.com, copilot.microsoft.com. Low volume today. Given its own bucket because the trend line is the point and it cannot be backfilled.
  • android-app:// scheme: new URL() parses these but .hostname returns the package name. Map explicitly: com.google.android.gm → email, com.linkedin.android → organic_social, com.google.android.googlequicksearchbox → organic_search. A regex expecting https:// silently drops all of these into unknown.

POST /e/collect — event ingest

  1. Gate: same-origin referer/origin check; accepts application/json and text/plain (sendBeacon sends text/plain); body ≤ 32 KB; per-IP token bucket (~10/min).
  2. Validate: email present and RFC-shaped; allowlisted keys; length caps.
  3. Bot signals — flag, never drop: honeypot website_url, form_age_ms < 2000, disposable email domain → sets bot_score. Reach ETL decides; no real lead is ever silently eaten.
  4. Identity merge: cookie pf_vid is authoritative; a divergent client ID rides along as visitor_id_client so Reach can stitch pre-migration history.
  5. Enrich: received_at, event_id = SHA-256(email + session_id + 60s bucket).
  6. Attach touch history: full ordered touches array from D1 (cap 50), each row carrying its derived channel, source, campaign, and touch_index. Flat first-touch fields kept for backward-compat with existing Reach mapping.
  7. Forward: POST to Reach, key appended server-side; retry ×3 (0.5s / 2s / 8s); terminal failure → dead_letters + alert. Browser always gets 204 — a Reach outage never blocks a visitor's submit.

GET /e/export — read path New

v3.1 had no way out of D1 except a form submit, which structurally excluded every visitor who never converted. Since RB2B exists precisely to identify those people, and since RB2B carries no channel data of its own, that gap made the person-level channel view impossible.

  • GET /e/export?since=<iso>&until=<iso>&cursor=<id>&table=touches|pageviews
  • Auth: Authorization: Bearer <EXPORT_KEY>. Never a query-string key — that is the mistake being retired at cutover.
  • Cursor-paginated on the autoincrement id, 1000 rows per page, stable ordering.
  • Reach pulls nightly. Assumed Reach can run a scheduled pull; if not, invert to a Worker cron that pushes. Decide with the Reach ETL owner before step 1, not after the schema is live.

D1 schema

CREATE TABLE touches (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  visitor_id TEXT NOT NULL, session_id TEXT,
  ts TEXT DEFAULT (datetime('now')),
  landing_page TEXT,                -- normalized path
  landing_url_raw TEXT,             -- full URL w/ query, for debugging
  referrer TEXT,
  referrer_host TEXT,               -- parsed; handles android-app://
  params TEXT,                      -- JSON of attribution params present
  channel TEXT NOT NULL,            -- derived, see classifier
  source TEXT, medium TEXT, campaign TEXT,
  touch_index INTEGER,              -- 1 = first touch for this visitor
  rules_version INTEGER NOT NULL,   -- which classifier wrote this row
  is_bot INTEGER DEFAULT 0,
  dedup_key TEXT UNIQUE             -- SHA-256(vid + params + host + 30m bucket)
);
CREATE INDEX idx_touches_visitor ON touches(visitor_id, ts);
CREATE INDEX idx_touches_channel ON touches(channel, ts);
-- retention: prune rows > 400 days (matches cookie life)

CREATE TABLE pageviews (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  visitor_id TEXT NOT NULL, session_id TEXT NOT NULL,
  ts TEXT DEFAULT (datetime('now')),
  path TEXT NOT NULL,               -- normalized, no query string
  query TEXT,                       -- raw query preserved separately
  referrer TEXT,
  touch_id INTEGER,                 -- FK: the touch that opened this session
  is_bot INTEGER DEFAULT 0
);
CREATE INDEX idx_pv_visitor ON pageviews(visitor_id, ts);
CREATE INDEX idx_pv_session ON pageviews(session_id, ts);
-- retention: 90 days raw, then roll up to daily path counts

CREATE TABLE dead_letters (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  event_id TEXT, payload TEXT NOT NULL, error TEXT,
  attempts INTEGER, created_at TEXT DEFAULT (datetime('now')),
  replayed_at TEXT
);

Why rules_version is worth a column. The channel taxonomy will change. When it does, this is the difference between reclassifying precisely the affected rows and guessing at date boundaries. It is the field people skip and then regret.

Why dedup_key mirrors event_id. Same SHA-256-plus-time-bucket pattern, 30 minutes instead of 60 seconds. Without it, a visitor who refreshes a UTM-tagged landing page three times produces three touches and the multi-source view fills with noise.

§6What this buys us New

The point of the build, stated in terms Taylor and Maren can hold. Everything here assumes the Reach ETL work in §8 lands; the endpoint produces the data, Reach produces the reporting.

Growth

  • Conversion rate by channel, computed two ways. First-touch and last-touch, side by side. The delta is the finding: channels weak on last-touch but strong on first-touch are discovery engines currently invisible.
  • Touches-to-conversion distribution. Highest-leverage number in the set. Decides whether to invest in top-of-funnel volume or in retargeting and nurture. No current read on it at all.
  • Time-to-conversion, first touch to submit. A 3-touch / 2-day journey and a 3-touch / 6-week journey imply different playbooks.
  • Assisted conversion rate per channel. Share of conversions where a channel appears in the path without being last.
  • New vs returning, trustworthy for the first time. The ITP fix means this stops being systematically wrong. Flag for the room: the returning rate will jump at cutover. That jump is measurement correcting, not growth.
  • Path depth and dropoff — entry page, pages per session, where people stop before /start/new.
  • Creator vs brand funnels, split. Two businesses on one domain. /creators drew 151 views against / at 385 in the RB2B slice, so this is not a rounding error. Persona-split is the only version of these metrics that means anything.

Marketing

  • Paid vs organic Google, separable. The 224 google.com referrers in the RB2B export decompose via gclid. Everything downstream of that split has been guesswork.
  • Campaign-level performance — which campaign, not just which channel.
  • Landing page by channel. The vertical pages (/pets, /skiing, /cycling, /adventure-travel, /hiking-and-backpacking) take real traffic with no current way to tell whether they feed /start/new or dead-end.
  • Campaign hygiene as a live measurable. The unknown bucket is the data-quality dashboard. Bare landing-page URLs in paid campaigns surface as a rising unknown count instead of silently inflating direct.
  • AI referral tracked from day one rather than backfilled never.
  • Referral program isolated. grsf separated from generic referral so GrowSurf is credited as its own channel.
  • Content-to-conversion path — whether blog traffic precedes conversions.

Sales

  • Lead context at handoff. Not "came from Google" but: paid search on the 12th, organic return on the 15th, direct on the 19th, viewed /platform/evergreens twice. That is a talk track.
  • Intent scoring with real inputs — touch count, session count, page depth, which pages. Rank the queue instead of working it chronologically.
  • RB2B-identified accounts with channel history. Inferred and contingent on the rb2b_id join landing. Person-level identity from RB2B plus channel history from this log gives sourced accounts that never filled a form.
  • Account-level buying-committee signal. Multiple people from one company touching from different channels. The current export already shows repeat companies.
  • Re-engagement triggers — known contact returns via a new channel. An alert, not a report.

Two caveats to put in front of Taylor and Maren before the first report, not after.

1. The first 90 days of multi-touch data will lie. The touch log starts empty at cutover. A visitor who first hit the site in March and converts in August looks like a one-touch visitor because the earlier touches do not exist. touch_index is wrong for every pre-launch visitor. Mitigation is the first_seen_before_launch flag in the payload contract: multi-touch analysis runs only on visitors whose first touch postdates deploy. Without it, the first read on touches-to-conversion is biased low and someone acts on it.

2. Volume will not support decisive channel comparisons for a while. /start/new drew 19 pageviews among RB2B-identified visitors; scaling by their stated 5–20% resolution rate puts total views in the low hundreds and form fills below that. Comparing conversion rates between two channels at that volume produces confidence intervals wide enough to drive a truck through. These metrics are directionally useful immediately and statistically decisive in months, not weeks.

The honest framing: this moves us from no attribution to correct attribution. Correct attribution at low volume is still mostly a qualitative instrument for the first quarter. It is the right build regardless, because the alternative is accumulating zero history while waiting for volume.
